# Text Humanizer v1.1 — Test Report & Product Listing

**File:** `index.html` (56.3 KB — limit 150 KB) · single file, all CSS/JS inline, zero external assets, zero network calls, no localStorage, no service workers, no permissions, no parent-window access. Safe for the sandboxed Wix iframe.
**v1.1 (20 Oct 2026)** adds multi-format document intake and five report exports; the analysis/humanizing engine is unchanged from v1.0.

## What it does
1. **Intake — paste, or upload a document:** .docx, .pdf, .rtf, .html/.htm, .odt, .txt, .md (up to 4 MB; extracted text capped at 20,000 characters with a clear notice). Real in-page parsers do the work: a ZIP+XML reader for Word/ODT files, an RTF interpreter (styles/destinations skipped, hex and unicode escapes decoded), an HTML text extractor (scripts/styles stripped), and a PDF text extractor (below). Legacy binary **.doc** is detected and refused with Save-As guidance — the OLE piece-table format cannot be read reliably in a web page, and the app says so instead of producing garbage.
2. **AI-style check (before):** stylistic score 0–100% from five signals (stock-phrase library, sentence-rhythm uniformity, formal-word density, contraction absence, vocabulary diversity), full metrics, and sentence-by-sentence **colour highlighting**.
3. **Humanize:** the rewriting engine (34 phrase rules, ~90 word swaps, contractions, rhythm ops) in 4 tones × 3 strengths.
4. **Re-check (after)** with the point reduction — then export the **full report** (scores, metrics, highlighted texts) in five formats:
   - **HTML** — styled report page.
   - **PDF** — generated by a real text-PDF writer inside the page (verified readable by poppler).
   - **DOCX** — a genuine Word file, built with a hand-written ZIP writer (stored entries + CRC32); verified by opening it with python-docx.
   - **DOC** — Word-compatible HTML document saved as .doc (opens in Word; labelled honestly as the HTML-based route, since the legacy binary format can't be authored in a page).
   - **JSON** — the complete structured record (scores, metrics, per-sentence classes, both texts).

## PDF intake — honest scope
PDF text lives in compressed content streams. The extractor inflates them (both Flate and ASCII85+Flate encodings — ReportLab-style files verified) and reads the text-showing operators. PDFs whose fonts are subset/encoded (many print pipelines, e.g. WeasyPrint output) or scanned images do not yield readable text this way; the app detects that and returns a clear message asking for copy-paste — it never shows garbage. There is no OCR in a web page at this size.

## The detector question — stated plainly
The score is a **stylistic estimate**, not a GPTZero, Turnitin, Originality.ai, Copyleaks or Pangram score, and **no tool can honestly guarantee a pass** on those proprietary, server-side, constantly retrained models. What is real: the app measures and removes the documented stylistic patterns such detectors weigh, and proves the change numerically. Genuine vendor scores would require paid APIs behind a key-holding backend (deployment plan in the v1.0 notes); Turnitin has no public self-serve API at all.
